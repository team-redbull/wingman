# Upgrade: 3.65 → 3.66 (a new NodePool is named after its InfraEnv)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 8) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.66.0` or a later 3.66 release.

## 1. What changes

A NodePool Wingman adds is named `<InfraEnv>` or `<InfraEnv>-<suffix>`, and
the name is written in the cluster file (ADR-0071). The InfraEnv part is the
nodepool's `infraEnvName`; a person adds only the suffix, so several
NodePools may draw from one InfraEnv. Existing NodePools keep their names.

| Area | 3.65 | 3.66 |
|---|---|---|
| The create form | **Nodepool Name**, free text, written only when typed; else the chart derives `<clusterName>-<infraEnvName>` | **Name suffix** beside the InfraEnv, the whole name previewed; every agent nodepool gets `name: <InfraEnv>[-<suffix>]` |
| A KV cluster's create | Its NodePool derived, `<clusterName>-<pool>` | `name: <pool>`, e.g. `r760-mtl-az1` |
| The flavor editor | `nodepool_name` among a nodepool's other inputs | `name_suffix` instead; a flavor with `nodepool_name` loads with a warning, and its save is refused until it presets `name_suffix` |
| Edit cluster | — | A **NodePool names** panel: existing names read-only, an added nodepool named from a suffix. Day1 refuses an added agent nodepool without `name: <infraEnvName>[-<suffix>]` |
| Refused (422, at the field) | Two nodepools deriving one name (by the chart, at sync) | A suffix that is not lowercase letters, digits and `-`; a name over 63 characters; two nodepools with one name; a create whose rendered file does not hold the name (the template, step 4) |
| Chart, Secrets, grants, settings, metrics | — | Nothing new |

The names Wingman writes now differ from the platform's acceptance tests,
which name NodePools `<cluster without ocp4->-<InfraEnv>` (kubevirt-workflows,
Acceptance Tests §3). The workflows read both shapes; record it for the team.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release. The reference template is
`dev/gitlab-fixtures/wingman/cluster-specs/cluster-template.j2` in that
repository.

## 3. Discover (read-only)

1. **The template.** In the specs project (`gitlab.specsProjectId`), open
   `cluster-template.j2` on the default branch and search it for
   `nodepool_name`.
   - `name: {{ np.nodepool_name }}` inside the nodepool loop
     (`{% for np in nodepools %}`), under `{% if np.nodepool_name | default("") %}`:
     the template writes the name. Step 4 is its comment only.
   - Not found: 3.66 refuses **every** create until step 4 is merged (422,
     `nodepool[0].name: the template wrote None for …`, naming this guide).
     Do step 4 before step 5.
   - Found in another shape (a `default` other than `""`, or `name:` written
     unconditionally from something else): **STOP** and report the lines.
2. **The comment above `name:`.** An older copy has a YAML comment there:

   ```yaml
       # Needed only when two nodepools share an InfraEnv; otherwise the chart
       # derives <clusterName>-<infraEnvName>.
   ```

   It is rendered into the file, and from 3.66 every new file has a name:
   record whether it is there (step 4 replaces it).
3. **Flavors that preset a whole name.** In the same project, search
   `specs/*.yaml` for `nodepool_name:`. Record each flavor. Each loads with a
   warning, and its next save is refused until the person who owns it
   presets `name_suffix` instead; a create from it is refused when the name
   does not follow the rule.

## 4. Change the template (a merge request in the specs project)

Only when step 3 found no `nodepool_name`, or the YAML comment. Inside the
nodepool loop, directly below the `infraEnvName:` line (and below
`additionalInfraEnvNames` when the template has it), the reference has:

```jinja
{% if np.nodepool_name | default("") %}
    {#- The NodePool's name: <InfraEnv> or <InfraEnv>-<suffix> (ADR-0071).
        Wingman passes it for every agent nodepool; a person adds only the
        suffix, so several nodepools may draw from one InfraEnv. No cluster
        prefix: each cluster's NodePools sit in its own hcp-<clusterName>.
        Without it the chart derives <clusterName>-<infraEnvName>, as older
        files have. #}
    name: {{ np.nodepool_name }}
{% endif %}
```

The `{#- … #}` is a Jinja comment: nothing of it reaches the file. Open the
merge request and have it reviewed and merged as any change of the specs
project. Wingman's form offers the suffix once the template reads
`nodepool_name`.

## 5. Upgrade

The [generic upgrade](README.md#the-generic-upgrade-no-guide) to `<tag>`:
the chart at `v<tag>` and the three images, with the values you already
have.

## 6. Verify

1. On **New Cluster**, pick a flavor: each nodepool row has a **Name suffix**,
   and below it the NodePool's whole name, the InfraEnv alone while the
   suffix is empty.
2. **Review** (it commits nothing): the rendered file has
   `name: <InfraEnv>` (or `<InfraEnv>-<suffix>`) under each nodepool, and no
   YAML comment above it.
3. Two nodepools on one InfraEnv with no suffix: Review stops at the second
   one's suffix ("NodePool … is nodepools[0]'s already").
4. **Edit cluster** on an existing cluster: the **NodePool names** panel
   lists its NodePools read-only, the derived ones as
   `<clusterName>-<infraEnvName>`.

## 7. Roll back

The images back to 3.65, the generic way. Files 3.66 wrote keep their
names, which 3.65 reads (`name`, else the derived one); nothing to undo.
The template change need not be reverted: 3.65 writes `name:` only when the
form gives it.

## 8. Report

What step 3 found (the template's lines, the comment, the flavors with
`nodepool_name`), the merge request of step 4 if any, the upgrade's result,
and step 6's checks.
