# Upgrade: 3.69 → 3.70 (a logical nodepool is a NodePool per zone)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 7) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.70.0` or a later 3.70 release.

## 1. What changes

A customer picks a **node type** (an InfraEnv's name without its zone:
`r760-mtl` for `r760-mtl-az1`..`az3`) and sets each zone's replicas; Wingman
writes one NodePool per zone of that node type on the MCE, every one with the
same configuration, named `<InfraEnv>[-<suffix>]` (ADR-0072). A zone may have
0 replicas: its NodePool is written anyway.

| Area | 3.69 | 3.70 |
|---|---|---|
| The create form | **Node type** picks one InfraEnv: one NodePool | **Node type** picks the kind of server; a row per zone with its replicas; one NodePool per zone |
| The cluster file | One `nodepool[]` entry per form nodepool | One entry per zone, each a plain entry (`infraEnvName`, `name`, `replicas`, the same configs and labels); **no new key** |
| The flavor editor | A nodepool presets an InfraEnv under Other inputs | A nodepool presets its **Node type**; an InfraEnv preset still works, one zone |
| Drift, sync, import | A flavor's nodepool is the file's entry at its position | It is the file's NodePools of one node type and suffix at that position; an older cluster keeps one entry per position |
| Refused (422) | — | A create whose rendered file does not write a zone's `replicas: 0` as 0 (the template, step 3) |
| Chart, Secrets, grants, settings, metrics | — | Nothing new |

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release. The reference template is
`dev/gitlab-fixtures/wingman/cluster-specs/cluster-template.j2` in that
repository.

## 3. Discover (read-only)

1. **The template's replicas.** In the specs project
   (`gitlab.specsProjectId`), open `cluster-template.j2` on the default branch
   and find the `replicas:` line inside the nodepool loop.
   - `replicas: {{ np.replicas | default(2) }}`: a 0 is written as 0. Nothing
     to change.
   - `default(2, true)`, `or 2`, or any other form that treats 0 as missing:
     3.70 refuses a create with a zone at 0 (422,
     `nodepool[1].replicas: the template wrote 2 for 0`, naming this guide).
     Open a merge request in the specs project that makes it
     `replicas: {{ np.replicas | default(2) }}`, as the reference has, and have
     it reviewed and merged as any change of that project.
   - Any other shape (replicas not from `np.replicas`): **STOP** and report
     the line.
2. **The InfraEnvs' names and zone labels** (optional, nothing breaks). On
   each Customer MCE, list the InfraEnvs:
   `oc get infraenvs -A -o custom-columns=NAME:.metadata.name,ZONE:.spec.agentLabels.topology\.kubernetes\.io/zone`.
   Names of the convention (`<flavor>-<mtl|kv<cpu>>-<zone>`) group into node
   types with their zones. A name off it is a node type of its own, in one
   zone (the label's, when it has one). Record the names that are off the
   convention: their customers see each as its own node type.
3. **Flavors that preset an InfraEnv.** In the specs project, search
   `specs/*.yaml` for `infra_env:`. Each still creates one NodePool in that
   zone; its owner may preset the node type instead (the flavor editor offers
   it). Record them.

## 4. Upgrade

The [generic upgrade](README.md#the-generic-upgrade-no-guide) to `<tag>`:
the chart at `v<tag>` and the three images, with the values you already
have.

## 5. Verify

1. On **New Cluster**, pick a flavor and an MCE: **Node type** lists node
   types with their zones. Pick one with several zones: a row per zone, each
   at the nodepool's replicas, each with its NodePool's name.
2. Set one zone to 0 and **Review** (it commits nothing): the rendered file
   has one `nodepool[]` entry per zone, `replicas: 0` in the one set to 0,
   and the same `configs` in each.
3. A cluster created before the upgrade: its drift and its **Sync** preview
   are what they were.

## 6. Roll back

The images back to 3.69, the generic way. Files 3.70 wrote are plain
cluster files with one entry per zone, which 3.69 reads; each NodePool is
then its own nodepool to 3.69, and a flavor's position the entry there.

## 7. Report

What step 3 found (the template's `replicas:` line and any merge request,
the InfraEnvs off the convention, the flavors that preset an InfraEnv), the
upgrade's result, and step 5's checks.
